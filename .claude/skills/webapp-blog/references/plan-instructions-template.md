# Plan 지침 파일 틀

`apps/{앱이름}/plan-instructions.md`로 저장한다. `{ }` 부분을 채우고, "특히 결정할 것"은 앱 종류에 맞게 고친다(게임이면 규칙·점수·승패, 도구면 기능·입출력·저장 형식 등).

---

```markdown
# Plan 서브에이전트 지침 — {앱 표시 이름}

## 역할
{앱 표시 이름} 웹앱의 구현 계획을 세우고 `apps/{앱이름}/spec.md`로 저장한다. **코드는 작성하지 않는다.**

## 요청 내용 (사용자 원문 요약)
- {사용자가 말한 기능 1}
- {기능 2}

## 수정 가능 범위
- `apps/{앱이름}/spec.md` 파일 생성만 허용한다.
- 그 외 파일은 읽기만 한다. 블로그 파일(`index.html`, `css/`, `js/`, `posts/` 등)과 다른 앱 폴더는 수정하지 않는다.
- git 명령은 실행하지 않는다.

## 참고할 것
- `CLAUDE.md`: 프로젝트 규칙 (자체 완결, 외부 라이브러리 최소화(CDN 허용), 모바일 지원, 블로그 색상 팔레트 사용, 사용법 안내 문구 필수)
- `apps/pixel-editor/spec.md`, `apps/2048/spec.md`: 이전에 승인된 계획서. **형식과 상세 수준을 이것에 맞춘다.** 테마(`localStorage.theme`)를 따르는 방식, 데모 모드로 `preview.png`를 만드는 방식, 순수 로직/UI 분리와 `tests.html` 등 이미 정한 관례를 재사용한다. **단, 두 앱의 "토큰 값 복사" 방식은 예전 방식이라 따르지 않는다.**
- `css/style.css`: 블로그 디자인 토큰과 전역 스타일. 앱 `index.html`에서 `../../css/style.css`를 먼저 불러오고, 앱 `style.css`는 `var(--…)`로 블로그 변수를 쓴다. 이 파일을 읽고 앱에 함께 적용되는 전역 규칙(`body`, 제목, 링크, 배경 등)을 확인한다.
- 나중에 블로그 `index.html`의 `ls apps/` 섹션에 카드(미리보기 이미지 + 링크)로 추가된다.

## spec.md에서 특히 결정할 것
1. **개요**: 앱 이름, 한 줄 설명, 블로그 카드 문구·분류·태그
2. **핵심 기능**: {앱 고유 기능}. 꼭 필요한 것과 범위 밖을 구분한다.
3. **사용법 안내**: 화면 어디에 어떤 문구로 넣을지(첫 화면 안내, 도움말 토글 등). 모바일·키보드 조작법 포함.
4. **색**: 블로그 `css/style.css`를 직접 불러오는 것이 기본이다. spec에는 ① `<link>` 순서, ② 블로그 전역 규칙 중 앱에서 덮어쓸 것, ③ 앱 전용 토큰(가능하면 `var(--neon)`처럼 블로그 변수로 정의)을 적는다. 불러오지 않는 쪽이 낫다고 판단되면 그렇게 정하지 말고 `## 사용자 확인 필요`에 이유와 함께 선택지로 올린다.
5. **작업 보존**: `localStorage` 사용 여부 (키 접두사 `apps.{앱이름}.`, try/catch, 손상된 값 처리)
6. **입력**: 마우스, 터치(Pointer Events, 스크롤 방지), 키보드(접근성)
7. **화면 구성**: 375px 모바일 기준, 640px/1024px 배치
8. **디자인**: 네온 테마 계승, 상태 표시, `prefers-reduced-motion`, 대비(WCAG AA), 터치 대상 44px
9. **파일 구조**: `apps/{앱이름}/` 아래 파일 목록과 역할
10. **로직 설계**: 순수 함수 시그니처, 자료형, DOM 없이 테스트 가능하게, `tests.html` 최소 케이스
11. **검증 기준**: Review 체크리스트 (어떻게 확인할지까지)
12. **범위 밖**: 이번에 하지 않을 것

## 작성 규칙
- 한국어로 작성한다.
- 간결하게, 구현자가 바로 따라 만들 수 있을 정도로 구체적으로 쓴다.
- 판단이 필요한 선택지가 있으면 추천안을 정하고, 마지막 `## 사용자 확인 필요` 절에 따로 적는다 (5개 안팎).
- `CLAUDE.md` 규칙과 다르게 가는 결정은 혼자 정하지 말고 반드시 `## 사용자 확인 필요`에 올린다. 사용자가 모르는 채로 규칙과 다른 계획을 승인하게 되기 때문이다.

## 완료 보고
작성을 마치면 spec.md의 핵심(파일 구조, 주요 결정, 확인 필요 사항)을 5~10줄로 요약해 보고한다.
```
