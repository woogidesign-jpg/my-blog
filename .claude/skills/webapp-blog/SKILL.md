# webapp-blog 하네스

이 블로그에 웹앱을 하나 추가하는 일은 **Plan → 승인 → Build → Review → Embed** 다섯 단계로 진행한다. 단계마다 서브에이전트를 쓰고, 각 서브에이전트에게는 전용 지침 파일을 만들어 넘긴다. 이렇게 하는 이유는 두 가지다. 사용자가 구현 전에 무엇을 만들지 확인할 수 있고, 만든 쪽과 검증하는 쪽을 나눠야 구현자의 착각이 검증을 통과하지 않기 때문이다.

프로젝트 루트에 `CLAUDE.md`가 있으면 그것이 최신 규칙이다. 이 스킬과 다르면 CLAUDE.md를 따르고, 다른 점을 사용자에게 알린다.

## 프로젝트 규칙 (CLAUDE.md 요약)

- 마크다운 기반 블로그 + 미니 웹앱 포트폴리오. HTML, CSS, JavaScript만 사용한다.
- 모든 웹앱은 `/apps/{앱이름}/` 폴더 안에 자체 완결된다. 블로그의 다른 파일은 Embed 단계 말고는 건드리지 않는다.
- 외부 라이브러리 사용을 최소화한다. CDN은 허용한다.
- 모바일에서도 사용할 수 있어야 한다.
- 모든 웹앱은 블로그의 색상 팔레트를 따른다. `css/style.css`의 CSS 변수를 참조한다. 기본은 앱 `index.html`에서 `../../css/style.css`를 직접 불러오는 것이다(기존 두 앱의 값 복사 방식은 따라 하지 않는다).
- 웹앱에 사용법 안내 문구를 반드시 포함한다.
- 서브에이전트에게 작업을 넘길 때 전용 지침 파일(.md)을 만들어 전달한다.
- Build 서브에이전트와 Review 서브에이전트는 반드시 분리한다.
- 서브에이전트는 지침 파일에 명시된 범위만 수정한다.
- **승인 없이 구현을 시작하지 않는다.** 막히면 사용자에게 알린다.

폴더 구조, 디자인 토큰, 기존 앱 목록, 카드 마크업, 개발 서버, git 관례는 `references/project-structure.md`에 있다. 새 앱을 시작할 때 한 번 읽는다.

## 0. 시작 준비

1. 앱 이름(폴더명)을 영문 소문자-하이픈으로 정한다. 예: `2048`, `pixel-editor`.
2. `git status`와 현재 브랜치를 확인하고, 이전 앱 브랜치가 `main`에 머지됐는지 본다(`git branch --merged main`). 머지되지 않은 앱 브랜치가 있으면 새 브랜치를 만들기 전에 사용자에게 알린다.
3. `main`에서 새 브랜치를 만든다(브랜치명 = 앱 이름). 앱마다 브랜치를 나누면 PR 하나가 앱 하나가 되어 리뷰와 되돌리기가 쉽다.
   - 커밋하지 않은 변경이 있으면 지우거나 stash하지 말고 그대로 새 브랜치로 가져간다(사용자 작업이다). 이번 앱과 관계없는 변경이라는 것을 사용자에게 한 줄로 알리고, Embed에서 커밋할 때 같이 넣을지 묻는다.
4. 작업 목록 도구가 있으면 다섯 단계를 올린다. 없으면 건너뛴다.

## 1. Plan — spec.md 작성

1. `apps/{앱이름}/plan-instructions.md`를 만든다. 틀은 `references/plan-instructions-template.md`. 사용자 요청 원문 요약과, 이 앱에서 특히 결정해야 할 항목(앱 종류에 맞게)을 채운다.
2. Plan 서브에이전트를 백그라운드로 띄운다. 프롬프트는 짧게: "지침 파일 `apps/{앱이름}/plan-instructions.md`를 읽고 그대로 수행하라." 환경에 따라 호출이 끝날 때까지 기다렸다가 결과를 돌려주기도 하는데, 그러면 바로 다음 순서로 넘어간다.
3. 끝나면 `spec.md`를 직접 읽고 점검한다. 특히 CLAUDE.md 규칙과 다른 결정(예: 블로그 `style.css`를 불러오지 않음)이 있는데 `## 사용자 확인 필요`에 올라가 있지 않으면, Plan 서브에이전트에게 SendMessage로 고치게 한다. 규칙과 다른 결정을 사용자 몰래 승인받게 하지 않기 위해서다.
4. 사용자에게 계획서를 보여 준다. 사용자는 계획을 **직접 보고** 승인하기를 원한다. 다만 전문을 채팅에 다 붙이면 수백 줄이 되어 읽기 어렵다. 그래서 다음 순서로 보여 준다.
   - `spec.md` 파일 링크
   - 절마다 1~3줄로 실제 결정 내용: 무엇을 넣고 뺐는지, 파일 구조, 색 처리, 사용법 안내 문구. "잘 정리했다" 같은 평가가 아니라 내용을 적는다.
   - `## 사용자 확인 필요` 항목 전부: 번호, 쉬운 말로 푼 선택지, 추천안
   - 승인하는 방법(예: "승인" 또는 "2번은 넣어 줘"), 그리고 전문을 원하면 바로 붙여 주겠다는 한 줄
5. **사용자 승인을 기다린다.** "승인" 또는 확인 항목에 대한 답이 오기 전에는 Build를 시작하지 않는다. 사용자가 고친 점은 spec.md에 반영한 뒤 다시 확인받는다.

## 2. Build — 구현

1. `apps/{앱이름}/build-instructions.md`를 만든다. 틀은 `references/build-instructions-template.md`. 사용자가 확정한 결정 사항을 그대로 적고, `references/lessons-learned.md`의 교훈 중 이 앱에 해당하는 것을 넣는다.
2. Build 서브에이전트를 백그라운드로 띄운다.
3. 완료 보고를 받으면 파일 목록, `tests.html` 결과, `preview.png` 생성 여부, 계획과 달라진 점을 확인한다.

## 3. Review — 독립 검증

1. `apps/{앱이름}/review-instructions.md`를 만든다. 틀은 `references/review-instructions-template.md`. Build가 보고한 "계획서와 달라진 점"과 "우려"를 우선 확인 항목으로 옮겨 적는다.
2. Build와 **다른** 새 서브에이전트를 띄운다. Review는 앱 코드를 고치지 않고 `review.md`만 쓴다.
3. 문제가 나오면 수정 요청은 **같은 Build 서브에이전트**에게 SendMessage로 보낸다(맥락을 이미 갖고 있다). 고친 뒤 재검증은 **같은 Review 서브에이전트**에게 보내고, review.md에 재검증 결과를 덧붙이게 한다.
4. 심각도 높음·중간 문제가 0이 될 때까지 반복한다. 낮음이나 "참고" 항목은 사용자에게 알리고 남겨도 된다.
5. 서브에이전트가 네트워크 오류 등으로 멈추면, 같은 에이전트를 SendMessage로 이어서 진행시키고 결과를 파일에 조금씩 써 두게 한다.

## 4. Embed — 블로그 카드 추가와 커밋

1. 블로그 `index.html`의 `<section class="apps">` 안 `.post-grid` **맨 앞**(최신이 먼저)에 카드를 넣는다. 마크업은 `references/project-structure.md`의 "앱 카드".
2. 같은 섹션의 `N apps` 숫자를 하나 올린다.
3. 브라우저에서 `http://localhost:8000/`을 열어 카드 이미지, 링크, 모바일 폭(375px)을 확인한다.
4. 커밋한다. 메시지는 한국어 한 줄 요약(예: `픽셀 아트 에디터 웹앱 추가`)과 맨 끝 Co-Authored-By 줄. spec·지침·review 파일도 함께 커밋한다(작업 기록으로 남긴다).
5. 푸시와 PR은 사용자가 요청할 때만 한다. 머지는 GitHub Pages 배포로 이어지므로 사용자 확인 후에만 한다.

## 사용자와 소통하는 방법

- 사용자는 한국어로 쉽게 설명받기를 원한다. 전문 용어는 짧게 풀어 쓴다.
- 백그라운드 서브에이전트가 아직 돌고 있을 때 턴을 끝내면, **"○○ 서브에이전트가 아직 작업 중이고, 끝나면 알림이 와서 이어서 진행한다"**고 분명히 말한다. 이전에 이 말이 없어서 사용자가 작업이 멈춘 줄 알았던 적이 있다.
- 서브에이전트 결과를 그대로 믿지 말고, 파일과 화면을 직접 확인한 뒤 보고한다.
- 커밋하지 않은 변경이 섞여 있으면 무엇을 커밋할지 사용자에게 묻는다.
